1 Что такое React: основы

React — библиотека для интерфейсов: страница собирается из компонентов. Изменил данные — интерфейс перерисовался сам. Используется в большинстве современных фронтендов.

  • React — JavaScript-библиотека (не фреймворк!) для построения пользовательских интерфейсов. Разработана Facebook/Meta, открыта в 2013.
  • Декларативность: описываешь «какой должен быть UI» (не «как»), React сам обновляет DOM.
  • Компоненты — строительные блоки: функции/классы, возвращающие разметку. UI = дерево компонентов.
  • Виртуальный DOM — лёгкая JS-копия настоящего DOM; React сравнивает и применяет только изменения.
  • Односторонний поток данных (вниз по дереву): родитель передаёт дочернему через props, данные не «гуляют» вверх сами.
  • Используется в SPA (одностраничные приложения), мобильных (React Native), десктопе (Electron), серверном рендеринге.
  • React не навязывает роутер, стейт-менеджмент, стили — это берётся из экосистемы. Next.js и др. добавляют «фреймворковые» удобства.
Ключевое отличие от фреймворков (Angular/Vue): React — это view-слой. Ответ «это библиотека, а не фреймворк» на собесе ценится.

2 Инструменты и сборка проекта

Инструменты: Vite или Create React App, npm, Babel, Webpack. Быстрый старт — create vite с шаблоном react, дальше npm run dev / build.

  • Vite — современный сборщик с dev-сервером (быстрый HMR). CRA (Create React App) — устаревший, но встречается в легаси.
  • npm/yarn/pnpm — менеджеры пакетов; package.json описывает зависимости и скрипты.
  • Код пишется на JSX/TS и компилируется: Babel или esbuild/oxc превращают JSX в React.createElement(...).
  • Точка входа: createRoot(document.getElementById('root')).render(<App/>) — рут-рендер с React 18+.
  • StrictMode — дев-режим, который нарочно дважды вызывает рендер и эффекты, чтобы отловить побочные эффекты.
  • HMR (hot module replacement) — обновление модуля без перезагрузки страницы, сохраняя состояние.
  • ESLint + Prettier — линт и форматирование; плагин eslint-plugin-react-hooks проверяет правила хуков.
Минимальный React 18+ bootstrap
import { createRoot } from 'react-dom/client';
import App from './App';

const root = createRoot(document.getElementById('root'));
root.render(<App />);

3 JSX — синтаксис разметки

JSX — HTML-подобный синтаксис внутри JS: const el =

Привет

. Внутри фигурных скобок { } — любые JS-выражения.

  • JSX — синтаксический сахар для createElement: «HTML-подобная» разметка прямо в JS.
  • Внутри { } можно вставлять любые JS-выражения: переменные, вызовы функций, тернарники, шаблонные строки.
  • Атрибуты в camelCase: className (не class), htmlFor (не for), onClick, tabIndex.
  • Условный рендер: {cond && <X/>}, тернарник, {cond ? <A/> : <B/>}, ранний return null.
  • Списки: .map() с обязательным атрибутом key (уникальный и стабильный — не индекс по умолчанию).
  • Строковые children, множественные children, Fragment <>...</> для возврата нескольких элементов без обёртки.
  • Комментарии в JSX: {/* ... */}. Имена тегов: строчные — DOM-элементы, с большой буквы — компоненты.
  • JSX — не шаблонный язык (не «строка»): это выражение, его можно присваивать, передавать, возвращать.
JSX: выражения и списки
const items = ['JSX', 'Props', 'State'];

function App({ isLogged }) {
  return (
    <div className="app">
      {isLogged ? 'Привет!' : 'Войдите'}
      <ul>
        {items.map((it, i) => (
          <li key={it}>{i + 1}. {it.toUpperCase()}</li>
        ))}
      </ul>
    </div>
  );
}

4 Компоненты

Компонент — кусок интерфейса: функция, которая возвращает JSX. Используется как тег: <Button />. Интерфейс собирается как конструктор.

  • Функциональный компонент — обычная функция, принимающая props и возвращающая JSX. Современный стандарт.
  • Классовый компонент — class extends Component с render(), this.state, lifecycle-методами. Легаси, но важно понимать.
  • Имя компонента — с большой буквы; вложенные компоненты не объявляй внутри других (будет ремоунт при каждом рендере).
  • Чистые компоненты: при одинаковых props/state отдавать одинаковый результат, без сайд-эффектов — залог предсказуемости.
  • Композиция — основной способ переиспользования: компоненты собираются из других, логика наследования почти не нужна.
  • children — специальный prop: то, что лежит между тегами. Позволяет делать «обёртки» и layout-компоненты.
  • Компоненты управляемые (controlled) — данные в state; неуправляемые — данные в DOM (через ref).
Функциональный компонент + композиция
function Card({ title, children }) {
  return (
    <div className="card">
      <h3>{title}</h3>
      {children}
    </div>
  );
}

function App() {
  return <Card title="Заголовок"><p>Любой JSX внутри</p></Card>;
}

5 Props — данные сверху вниз

Props — параметры компонента, данные передаются сверху вниз: <User name="Аня" />. Родитель → ребёнок, один поток данных.

  • Props (properties) — входные данные компонента: объект, который нельзя мутировать (immutable).
  • Типы значений: примитивы, объекты, массивы, функции-колбэки, JSX (render props / children), компоненты.
  • Деструктуризация: function Card({ title, onClick }) {...} — читабельно и с дефолтами: { title = 'Нет' }.
  • Колбэки вниз + события вверх — стандарт: <Button onClick={handler}/>, обработчик определён в родителе.
  • defaultProps (классы) и значения по умолчанию при деструктуризации (функции) — значение по умолчанию для отсутствующего prop.
  • Prop drilling — передача prop через много уровней. Лечится Context или стейт-менеджментом (но без фанатизма).
  • Rest props (...rest) — «проброс» лишних атрибутов в DOM-элемент, например для a11y-атрибутов.
  • Валидация: PropTypes (устаревает) или TypeScript — интерфейсы для props.
Запомни: «поток данных один — вниз», «события вверх». Если видишь мутацию props — это баг.

6 State — состояние компонента

State — данные компонента, которые могут меняться: useState. Изменил state — компонент перерисовался с новыми данными.

  • State — данные, которые меняются со временем; локальны для компонента и хранятся между рендерами.
  • useState — хук состояния: const [count, setCount] = useState(0). Возвращает [значение, сеттер].
  • Обновление — всегда через сеттер (setCount), никогда не мутируй state напрямую.
  • Сеттер можно вызывать с новым значением или с функцией: setCount(c => c + 1) — функциональная форма безопасна при нескольких обновлениях подряд.
  • Обновления батчатся: несколько setState в одном обработчике = один ререндер (React 18 — авто-батчинг даже в промисах).
  • State не обновляется мгновенно (асинхронно, до рендера) — не читай его сразу после setState; читай через эффекты или вычисли при рендере.
  • Объекты и массивы в state обновляй через копии: setUser({...user, name}), setItems([...items, item]) (иммутабельность).
  • Подъём состояния (lifting state up) — вынести state в общего родителя, чтобы несколько детей им делились.
  • Деривированное состояние — вычисляется из props/state при рендере, в отдельный state не дублируем (лишний state = источник багов).
useState + функциональное обновление
function Counter() {
  const [count, setCount] = useState(0);

  const inc3 = () => {
    setCount(c => c + 1);
    setCount(c => c + 1);
    setCount(c => c + 1); // результат: +3 за один клик
  };

  return <button onClick={inc3}>{count}</button>;
}

7 События и формы

События: onClick, onChange, onSubmit. Формы — управляемые компоненты: value связан с state, изменения через onChange.

  • Синтетические события — React оборачивает нативные события в кросс-браузерную обёртку SyntheticEvent.
  • Обработчики: onClick, onChange, onSubmit, onKeyDown и т.д.; событие передаётся первым аргументом: onClick={(e) => ...}.
  • Контекст: в функциональных компонентах this не нужен (замыкание); в классах — биндинг onClick={this.handle.bind(this)} или стрелочные поля.
  • Формы: controlled — value из state + onChange; uncontrolled — значение живёт в DOM (читаем через ref).
  • Остановка дефолта: e.preventDefault() (submit формы), e.stopPropagation().
  • Радио/чекбоксы/select — тоже controlled; textarea использует value, не содержимое.
  • Паттерн «single source of truth»: state — единственный источник для формы; лёгкая валидация и «reset». react-hook-form/Formik — для сложных форм.
  • React 19: Form Actions — <form action={fn}> вызывает функцию с FormData, поддержка <button formAction>.
Controlled input
function Login() {
  const [email, setEmail] = useState('');

  return (
    <form onSubmit={(e) => { e.preventDefault(); console.log(email); }}>
      <input value={email} onChange={(e) => setEmail(e.target.value)} />
      <button type="submit">Войти</button>
    </form>
  );
}

8 Рендеринг и реконсиляция

Рендеринг — отрисовка интерфейса. Реконсиляция — React сравнивает старое и новое дерево и обновляет только изменившиеся части DOM.

  • Каждый рендер — «снимок» UI: компонент вызывается заново, JSX строится, React сравнивает с прошлым деревом.
  • Реконсиляция (diffing) — алгоритм сравнения виртуальных деревьев; изменения применяются в DOM минимально.
  • Рендер вызывается: при изменении state, при новых props, при рендере родителя (по умолчанию — даже если props не менялись).
  • Fiber — внутренняя структура React 16+: работа разбита на единицы, поддержка паузы/приоритетов (concurrent rendering).
  • Фазы: render (построение VDOM) и commit (применение в DOM + запуск эффектов). Render-фаза не должна иметь сайд-эффектов.
  • key помогает React сопоставлять элементы списка при переупорядочивании — неправильный key = пересоздание элементов/потеря state.
  • Suspense — «приостановка» рендера до готовности данных/кода, отображает fallback.
  • Почему повторяющийся рендер родителя перерисовывает детей: по умолчанию дети рендерятся вместе с родителем; мемоизация оптимизирует это.
На собесе: «почему React перерисовывает компонент?» → 1) изменился state 2) изменились props 3) ререндер родителя. Плюс Context.

9 Хуки: правила и обзор

Хуки — функции для state и эффектов: useState, useEffect, useRef, useMemo. Правила: только на верхнем уровне, только внутри функциональных компонентов.

  • Хуки (React 16.8, 2019) — функции для состояния и lifecycle-логики в функциональных компонентах.
  • Правила хуков: 1) только на верхнем уровне (не в циклах/условиях/вложенных функциях); 2) только из React-функций (компонент или другой хук).
  • Порядок хуков стабилен от рендера к рендеру — так React сопоставляет состояние с вызовами; условный вызов ломает порядок (eslint это ловит).
  • Кастомные хуки начинаются с use: function useWindowWidth() {...} — композиция логики.
  • Основные: useState, useEffect, useRef, useMemo, useCallback, useReducer, useContext.
  • Реже: useLayoutEffect (синхронно после DOM-мутаций), useInsertionEffect (для стилей), useImperativeHandle.
  • React 19: use() (читает Promise/Context вне эффектов), useActionState, useOptimistic, useTransition.
  • Библиотека @tanstack/react-query и другие — построены на кастомных хуках.
Правило №1 на собесе: «не вызывай хуки в условиях» — из-за порядка вызова, а не «потому что так нельзя».

10 useEffect — эффекты и жизненный цикл

useEffect — побочные эффекты: запросы к API, подписки, таймеры. Второй аргумент — массив зависимостей, от него зависит, когда эффект перезапустится.

  • useEffect(cb, deps) — побочные эффекты: подписки, таймеры, fetch, манипуляции вне React.
  • Выполняется после коммита в DOM (асинхронно, после отрисовки). Аналог componentDidMount + componentDidUpdate + componentWillUnmount.
  • Массив зависимостей deps: [] — один раз (mount); [a, b] — при изменении; без массива — после каждого рендера.
  • Cleanup-функция: return () => ... — отписка/очистка перед следующим эффектом и при размонтировании.
  • Опасности: лишние зависимости вызывают повторные эффекты; «пустые» зависимости + используемые переменные → устаревшие значения (stale closure).
  • В StrictMode (dev) эффекты запускаются дважды — это не баг, а проверка корректности cleanup.
  • Если что-то вычисляется из state/props — не эффект, а вычисление при рендере; эффект для синхронизации с «внешним миром».
  • Объекты/функции в deps создают новый ref каждый рендер → эффект срабатывает каждый раз; лечится useMemo/useCallback.
useEffect + cleanup (подписка/таймер)
useEffect(() => {
  const id = setInterval(() => setTick(t => t + 1), 1000);
  return () => clearInterval(id); // cleanup
}, []);

11 useRef — ссылки без ререндера

useRef — ссылка на DOM-элемент или любые данные. Главное отличие от state: изменение ref не вызывает перерисовку.

  • useRef(init) — «ящик» с mutable-значением: const ref = useRef(null); доступ через ref.current.
  • Изменение ref.current НЕ вызывает ререндер (в отличие от state). Один объект живёт всю жизнь компонента.
  • Для DOM: <input ref={ref} /> → ref.current = DOM-узел (после mount). Полезно для фокуса, замера, интеграции со старыми библиотеками.
  • Для «мутабельных значений»: id таймера, счётчик кликов, последнее значение (для сравнения), stash для анимаций.
  • Чтение ref.current в эффекте — типичная работа: не вызывай сайд-эффекты напрямую в рендере.
  • useImperativeHandle — выставить методы наружу через ref (вместе с forwardRef).
  • forwardRef — проброс ref через функциональный компонент (React 19: ref — обычный prop, forwardRef не обязателен).
  • Отличие от state: ref — «память без ререндера», state — «память с ререндером». Выбор: что рендерится → state, что «служебное» → ref.
ref: фокус + хранение значения без ререндера
function NameForm() {
  const inputRef = useRef(null);
  const renderCount = useRef(0);

  useEffect(() => { inputRef.current?.focus(); }, []);

  const onClick = () => {
    renderCount.current += 1; // не вызывает ререндер
    console.log(inputRef.current.value, renderCount.current);
  };

  return <><input ref={inputRef} /><button onClick={onClick}>Ok</button></>;
}

12 Мемоизация: useMemo, useCallback, memo

Мемоизация — кэширование вычислений против лишних перерисовок: useMemo — результат, useCallback — функция, memo — сам компонент.

  • useMemo(fn, deps) — кеширует вычисляемое значение; пересчитывается только при изменении deps.
  • useCallback(fn, deps) — кеширует саму функцию (стабильная ссылка между рендерами).
  • React.memo(Component) — мемоизированный компонент: пропускает ререндер, если props не изменились (поверхностное сравнение).
  • Связка: React.memo + useCallback — колбэки со стабильной ссылкой не ломают мемоизацию детей.
  • Используй, когда вычисление дорогое (сортировки, фильтрации, обработка больших данных) или передаёшь колбэки в мемоизированные дети.
  • Антипаттерн: оборачивать всё подряд в useMemo/useCallback «на всякий случай» — сам сравнение deps тоже стоит времени. Измеряй.
  • React Compiler (в React 19+) автоматически мемоизирует код — ручные memo/useMemo постепенно становятся необязательными.
  • Не мемоизируй то, что и так дёшево: примитивы, простые JSX; мемоизация полезна для объектов/функций, передаваемых в мемоизированных детях.
Классический вопрос собеса: «useMemo vs useCallback» → useMemo возвращает результат, useCallback возвращает функцию. Оба — про стабильную ссылку.

13 useReducer — сложный state

useReducer — управление сложным состоянием через reducer (как в Redux): событие → новый state. Для форм, корзин, машин состояний.

  • useReducer(reducer, initialState) — альтернатива useState для сложной логики переходов состояния.
  • Паттерн: const [state, dispatch] = useReducer(reducer, init); dispatch(action) — отправка «действия».
  • reducer(state, action) => newState — чистая функция: из старого state и action получает новый state, без мутаций и сайд-эффектов.
  • Action — объект: { type: 'INCREMENT', payload: 1 }. Имена через константы/типы — меньше опечаток.
  • Полезен, когда несколько полей state меняются вместе, есть сложные переходы, или логика обновления переиспользуется.
  • Ленивая инициализация: третий аргумент init(initialArg) — тяжёлые вычисления только при первом рендере.
  • Рекомендация: редьюсеры удобно юнит-тестировать как чистые функции — отдели их от компонента.
  • Вместо «setState+if» с кучей обработчиков: один dispatch с type — состояние переходит предсказуемо. Основа Redux-идеологии.
useReducer: счётчик с переходом
function reducer(state, action) {
  switch (action.type) {
    case 'INCREMENT': return { count: state.count + 1 };
    case 'RESET': return { count: 0 };
    default: return state;
  }
}

function Counter() {
  const [state, dispatch] = useReducer(reducer, { count: 0 });
  return (
    <>
      <b>{state.count}</b>
      <button onClick={() => dispatch({ type: 'INCREMENT' })}>+</button>
      <button onClick={() => dispatch({ type: 'RESET' })}>0</button>
    </>
  );
}

14 Context — глобальные данные

Context — глобальные данные без прокидывания props через все уровни: тема, юзер, язык. createContext + Provider, доступ через useContext.

  • Context — способ передавать данные в глубоко вложенные компоненты без проброса через каждый уровень (тема, язык, пользователь).
  • Создание: const Theme = createContext('light'); использование: useContext(Theme).
  • Провайдер: <Theme.Provider value="dark">...</Theme.Provider> — все потребители внутри получают value.
  • Любой компонент, использующий useContext, ререндерится при изменении value (даже с React.memo) — это и плюс, и минус.
  • Разделяй контексты по смыслу (Theme, User, Locale) — единый «большой контекст» вызывает лишние ререндеры.
  • Значение мемоизируй: value={useMemo(() => ({user, setUser}), [user])} — чтобы не менять ссылку каждый рендер.
  • Контекст — не замена стейт-менеджменту для сложных данных: для частых обновлений многих потребителей лучше Redux/Zustand (+ селекторы).
  • Реактивные паттерны: reducer + context — мини-Redux без зависимостей.
Context: тема
const Theme = createContext('light');

function App() {
  return (
    <Theme.Provider value="dark">
      <Toolbar />
    </Theme.Provider>
  );
}

function Toolbar() {
  const theme = useContext(Theme);
  return <div className={theme}>Toolbar</div>;
}

15 Классовые компоненты и жизненный цикл

Классовые компоненты — старый способ: class, render(), state = {}, componentDidMount. Сейчас в основном пишут на хуках, но спрашивают и это.

  • class X extends React.Component: state в конструкторе, this.setState(), render() обязателен.
  • Mount: componentDidMount — после вставки в DOM (подписки, fetch).
  • Update: componentDidUpdate(prevProps, prevState) — после обновления (сравнение, ответ на изменения).
  • Unmount: componentWillUnmount — очистка (отписки, таймеры).
  • Отмена/оптимизация: shouldComponentUpdate — вернуть false, чтобы пропустить ререндер; PureComponent — автоматическое поверхностное сравнение.
  • componentWillMount/componentWillReceiveProps/componentWillUpdate — легаси-методы (UNSAFE_), избыточны с современным подходом.
  • getSnapshotBeforeUpdate — чтение DOM до применения изменений (редко).
  • Привязка this в классах: стрелочные поля или bind в конструкторе — иначе потеря контекста в обработчиках.
  • Сегодня: функциональные компоненты + хуки — мейнстрим; классы — легаси, но на собесе спрашивают понимание.
Сопоставление: didMount ≈ useEffect(cb, []), didUpdate ≈ useEffect(cb, [deps]), willUnmount ≈ cleanup в useEffect.

16 React Router — маршрутизация

React Router — переходы между страницами без перезагрузки: BrowserRouter, Routes, Route, useNavigate, useParams, Link.

  • React Router — стандартный роутер для SPA: навигация без перезагрузки страницы (роутинг на клиенте).
  • Версии: v6/v7 (декларативные <Routes>), v5 (устаревшие <Switch>). react-router-dom — для веба.
  • Обёртка: <BrowserRouter> (history API) или <HashRouter> (#/path).
  • Маршруты: <Routes><Route path="/" element={<Home/>} /><Route path="/users/:id" ... /></Routes>.
  • Навигация: <Link to="/users/1"> (анкор), <NavLink> (+ active), программно — useNavigate().
  • Параметры: useParams() → { id }, query — useSearchParams().
  • Вложенные маршруты и <Outlet> — layout-обёртки с общим меню; индексный роут index.
  • Защита маршрутов: компонент-обёртка RequireAuth — проверяет авторизацию и редиректит (<Navigate to="/login" replace />).
  • Ленивые роуты: element={<Suspense fallback={...}><LazyHome/></Suspense>} — код сплитится по страницам.
  • Настройки: <Navigate to="/" /> — редирект по умолчанию; * — 404-страница.
React Router v6
function Layout() {
  return (<><nav><Link to="/">Home</Link></nav><Outlet /></>);
}

function App() {
  return (
    <BrowserRouter>
      <Routes>
        <Route element={<Layout />}>
          <Route index element={<Home />} />
          <Route path="users/:id" element={<User />} />
        </Route>
      </Routes>
    </BrowserRouter>
  );
}

17 Управление состоянием (state management)

State management — глобальное состояние приложения: Redux, Zustand, Context. Нужно, когда state растекается по всему приложению.

  • Локальный state (useState) + Context — достаточно для большинства задач; библиотеки — для масштаба и сложных обновлений.
  • Redux — предсказуемый контейнер состояния: единое хранилище, редьюсеры, подписка.
  • Redux-принципы: single source of truth (один store), state read-only (меняется только action-ами), изменения — чистыми редьюсерами.
  • Redux Toolkit (RTK) — современный стандарт: createSlice, автоматический Redux DevTools, createAsyncThunk.
  • Zustand — лёгкий store на хуках без Provider-ов и бойлерплейта; популярен в новых проектах.
  • Селекторы: useSelector((state) => state.user) — подписка на часть стора; некорректные селекторы = лишние ререндеры.
  • Middleware: redux-thunk, redux-saga — асинхронная логика и сайд-эффекты в экшенах.
  • Серверный state (данные с API) — отдельно: TanStack Query/SWR, а не в Redux-стор (кэш, рефетчи, invalidation).
  • «Когда нужен Redux?» — сложное общее состояние (корзина, авторизация), команды, отладка через DevTools; для малого — перебор.
Собеседование: «Context vs Redux?» → Context для статичных/редко меняющихся данных; Redux/Zustand для частых обновлений с селекторами и девтулзами.

18 Оптимизация производительности

Оптимизация: мемоизация, code splitting (lazy/Suspense), виртуализация списков, меньше лишних ререндеров. Инструмент — React DevTools Profiler.

  • Измеряй до оптимизации: React Profiler (DevTools) показывает длительность рендеров и причины.
  • React.memo — пропуск ререндера при тех же props (поверхностное сравнение).
  • Стабильные ссылки: useCallback/useMemo — для функций/объектов, передаваемых в мемоизированных детях.
  • Корректные key — меньше пересозданий элементов списка.
  • Code splitting: lazy(() => import('./Widget')) + Suspense — загрузка кода по требованию, «куплеты» бандла.
  • Выноси тяжёлые поддеревья и фильтрации; деривированные значения — в useMemo при дорогих вычислениях.
  • Virtualization (react-window, react-virtualized) — рендер только видимых строк огромных списков.
  • Избегай создания новых объектов/функций в JSX-пропах на каждый рендер, если это ломает memo-детей.
  • React Compiler (React 19) автоматически мемоизирует — ручная оптимизация отходит на второй план.
Золотое правило: сначала чини причины ререндеров (структура), потом мемоизация. Не оптимизируй вслепую.

19 SSR, Next.js и Server Components

SSR — рендер на сервере для скорости и SEO. Next.js — фреймворк поверх React. Server Components — часть логики и рендера на сервере.

  • SSR — рендер HTML на сервере: быстрый первый отклик, SEO, нет «пустой» страницы.
  • Hydration — «оживление» серверного HTML на клиенте: навешивание обработчиков без перерисовки.
  • Next.js — React-фреймворк: файловый роутинг, SSR/SSG/ISR, API-роуты, деплой на Vercel.
  • SSG (static generation) — HTML собирается на сборке; ISR — ревалидация статики по расписанию.
  • React Server Components — компоненты, выполняющиеся только на сервере: без клиентского JS, доступ к БД напрямую.
  • Модель использования: use client (клиентский компонент) / use server (серверные actions) — маркировка границы.
  • Серверные данные + Streaming: HTML отдаётся по частям (Suspense-секции).
  • «Метафреймворки»: Next.js, Remix, Gatsby (SSG), Astro — выбор зависит от задачи (SSG-блог vs SSR-приложение).
Вопрос собеса: «SSR vs SPA?» → SSR: SEO, быстрый FCP, хуже для сильной интерактивности; SPA: плавность, нагрузка на клиента.

React 19: Actions, useOptimistic, useActionState, Server Components стабильны, ref можно передавать как prop, улучшенный Hydration.

  • Form Actions: <form action={serverFn}>, action={fn} в компонентах, useActionState.
  • useActionState(fn, init) — асинхронный action + состояние и pending; action={fn} в `
    `.
  • useOptimistic — оптимистичные обновления UI до ответа сервера (откат при ошибке).
  • use() — читает Promise/Context внутри компонента без хука-обёртки; работает в условных ветках.
  • useTransition — «неблокирующие» обновления с приоритетом (раньше было в 18).
  • ref как обычный prop (без forwardRef); useId для уникальных id; useDeferredValue.
  • React Compiler — автоматическая мемоизация, релиз 1.0 (октябрь 2025); babel-плагин в сборке.

Вопрос собеса 2026: «Что нового в React 19?» → actions, useActionState, useOptimistic, use(), React Compiler, RSC, ref-as-prop.

21 TypeScript + React

TypeScript — JS с типами: interface, type, типизированные props, useRef. Меньше багов и лучше автодополнение в IDE.

  • TypeScript — статическая типизация поверх JS; в React — безопасные props, стейт, события.
  • Props: type Props = { name: string; count?: number; onClick: (id: string) => void }.
  • ReactNode — тип children (строка, элемент, массив, null); ReactElement — именно элемент.
  • События: ChangeEvent<HTMLInputElement>, MouseEvent<HTMLButtonElement>, FormEvent<HTMLFormElement>.
  • useState: useState<string | null>(null) или вывод типа автоматически; для объектов — useState<User>({...}).
  • useRef: useRef<HTMLInputElement>(null) → ref.current?.focus(); mutable — useRef<number>(0).
  • useReducer с типизированными action-ами: { type: 'INC' } | { type: 'SET'; value: number } — исчерпывающие ветки.
  • Generic-компоненты: function List<T>({ items }: { items: T[] }) — переиспользуемые списки.
  • FC/FunctionComponent — необязательно; типизация props без обёртки читается лучше.
  • Строгие настройки: strict: true (noUncheckedIndexedAccess, exactOptionalPropertyTypes) — защита от `undefined`.
Типизированные props и события
type Props = {
  label: string;
  onSave: (value: string) => void;
};

function Input({ label, onSave }: Props) {
  return (
    <input
      placeholder={label}
      onChange={(e: ChangeEvent<HTMLInputElement>) => onSave(e.target.value)}
    />
  );
}

22 Тестирование React

Тесты: Jest + React Testing Library (тесты поведения), Vitest, Playwright для e2e. render, fireEvent/userEvent, screen.getByRole.

  • Пирамида: юнит (логика/компоненты) → интеграционные → e2e (Playwright/Cypress).
  • React Testing Library (RTL) — тест «как пользователь»: рендер, поиск по ролям/тексту, взаимодействия.
  • Vitest (быстрый, Vite-совместимый) или Jest — runner + asserts + mocks.
  • Рендер: render(<Component />), запросы: getByRole, getByText, getByLabelText (a11y-friendly).
  • Действия: fireEvent/userEvent (реалистичнее); асинхронные — findBy*, waitFor.
  • act() — обёртка React для уведомления о ререндерах в тестах; RTL делает это за тебя.
  • Снапшоты: toMatchSnapshot — для регрессии разметки (не злоупотребляй).
  • Мок-зависимости: fetch-модули, таймеры (vi.useFakeTimers()), resizeObserver, matchMedia — замакь то, что тестируемому компоненту не нужно.
  • Совет: тестируй поведение (что видит/делает пользователь), а не внутренности (не рендери реализацию через shallow).

23 Паттерны React

Паттерны: custom hooks, render props, compound components, HOC, порталы. Способы переиспользования логики и разделения ответственности.

  • Композиция вместо наследования: props, children, передача JSX.
  • HOC (Higher-Order Component) — функция, возвращающая обёрнутый компонент (withAuth(Wrapped)); классика, но часто заменяется хуками.
  • Render props — проп-функция, возвращающая JSX: <Data fetcher={(data) => ...} />.
  • Compound Components — группа компонентов, работающих с общим контекстом: <Tabs><Tabs.List>...<Tabs.Panel>....
  • Controlled / Uncontrolled — управление данными через props или через внутренний ref.
  • Кастомные хуки — вынос логики (fetch, resize, debounce, localStorage).
  • Порталы — рендер в другой DOM-узел (модалки, тултипы) без потери контекста событий.
  • Границы: Error Boundary — ловля ошибок рендера; Suspense — fallback для отложенного контента.
Собеседование: «HOC vs render props vs hooks» → все про переиспользование логики; хуки — современный, читаемый способ.

24 Error Boundaries и обработка ошибок

Error Boundaries — ловят ошибки при рендере и показывают запасной UI вместо падения всего приложения. Классовые компоненты с componentDidCatch.

  • Error Boundary — классовый компонент (componentDidCatch / static getDerivedStateFromError), ловящий ошибки в дочернем дереве.
  • Ловит ошибки рендера, жизненного цикла, конструкторов; НЕ ловит: обработчики событий, async-код, SSR, сами ошибки Error Boundary.
  • Ошибки в обработчиках событий: try/catch вручную или отправка в Sentry/мониторинг.
  • React 19: Error Boundaries могут быть функциональными компонентами? — пока классовые, но с новым хуком useErrorBoundary (в разработке); в 19 поддержка error-boundary-функциональных через новое API расширяется.
  • Fallback-UI: getDerivedStateFromError → рендерим запасную страницу/кнопку «перезагрузить».
  • Reset состояния границы: по клику «Попробовать снова» сбрасываем ключ (key) — пересоздание дерева.
  • Sentry/ErrorBoundary от библиотек — готовые решения с логированием и ретраями.
Error Boundary (класс)
class ErrorBoundary extends React.Component {
  state = { error: null };
  static getDerivedStateFromError(error) {
    return { error };
  }
  componentDidCatch(error, info) {
    console.error(error, info);
  }
  render() {
    if (this.state.error) {
      return <h1>Что-то пошло не так</h1>;
    }
    return this.props.children;
  }
}

25 Стилизация в React

Стилизация: CSS-модули, Tailwind, styled-components, инлайн-стили, CSS-in-JS. classNames — для условных классов.

26 Работа с данными: fetch и кэш

Данные: fetch/axios в useEffect, TanStack Query (кэш запросов), Suspense. Загрузка, ошибки, лоадеры — три состояния любого запроса.

  • Базово: fetch(url) + useEffect + состояние загрузки/ошибки — самописный хук useFetch.
  • Гонки/отмены: ignore-флаг или AbortController в cleanup — избежать setState после размонтирования.
  • TanStack Query (react-query) — серверный state: кэш, рефетчи, инвалидация, ретраи, devtools.
  • SWR (Next.js) — лёгкий альтернативный кэшер данных; «stale-while-revalidate».
  • Мутации: useMutation + оптимистичные обновления (или useOptimistic в React 19).
  • Запросы: useQuery — данные + кэш + refetch; серверные мутации — через useMutation.
  • Библиотеки не нужны, если данных мало и они редки — решай по задаче, не «по моде».
  • Кэширование — это не про Redux: серверные данные кешируются query-клиентом, глобальное UI-состояние — store.
  • SSR/SSG-варианты: fetch в серверных компонентах (Next.js) — без waterfall-цепочки клиентских запросов.
Самописный useFetch с отменой
function useFetch(url) {
  const [data, setData] = useState(null);
  const [error, setError] = useState(null);

  useEffect(() => {
    const ctrl = new AbortController();
    fetch(url, { signal: ctrl.signal })
      .then(r => r.json())
      .then(setData)
      .catch(setError);
    return () => ctrl.abort(); // отмена при размонтировании
  }, [url]);

  return { data, error };
}

27 Экосистема и сравнение с другими

Экосистема: React vs Vue vs Angular. React — библиотека с большой экосистемой, Vue — проще для входа, Angular — полный фреймворк из коробки.

  • React vs Vue: Vue — фреймворк с шаблонами и реактивностью; React — библиотека с JSX и VDOM. Субъективный выбор, оба популярны.
  • React vs Angular: Angular — полный фреймворк (DI, TypeScript обязателен, формы, роутер); React — гибкость, свои решения.
  • Svelte — компилятор без VDOM, малый рантайм; Solid — сигналы, реактивность без VDOM.
  • Мета-фреймворки: Next.js (React), Nuxt (Vue), SvelteKit, Remix — SSR/SSG из коробки.
  • Мобильные: React Native, Expo; десктоп: Electron, Tauri (webview).
  • Тестирование/качество: Vitest, RTL, ESLint, CI (GitHub Actions) — стандартный стек.
  • Государство: Zustand, Redux Toolkit, Jotai, Recoil — «выбирай по размеру проекта и команде».
  • Тренды 2026: React Compiler, RSC, AI-инструменты (Codium/Copilot) в разработке, Perf-фокус на хуках.
Собеседование: «Почему React, а не Vue/Angular?» → экосистема, гибкость, RSC/SSR-экосистема Next.js, сообщество, типы.

28 Отладка и DevTools

Отладка: React DevTools (Components + Profiler), console.log, breakpoints в браузере, Redux DevTools для состояния. Начни с DevTools.

  • React DevTools — вкладка Components: props, state, дерево; Profiler — длительность рендеров.
  • Профилирование: включи Profiler, запиши взаимодействие, найди «красные» компоненты с частыми/дорогими рендерами.
  • Почему компонент ререндерится: фильтр в DevTools (Highlight updates) — подсветка обновляемых узлов.
  • why-did-you-render — библиотека-помощник для выявления лишних ререндеров.
  • Логика состояния: Redux DevTools — time-travel, action history; Zustand — своя вкладка.
  • Типовые ошибки: «нет key», «мутация state», «эффект каждый рендер», «StrictMode-дубли», «утечка подписки».
  • Ошибки в консоли — читать до конца, sourcemap-ы ведут в исходники (не в бандл).
Рабочий навык: включить Profiler → записать → найти причину лишнего ререндера → починить мемоизацией/структурой.

29 Частые вопросы собеседования

Частые вопросы: зачем key в списках, разница state и props, жизненный цикл, controlled vs uncontrolled, event delegation, чистые компоненты.

  • «Почему useState не обновляет значение сразу?» — батчинг, значение обновится к следующему рендеру.
  • «Зачем key и что будет без него?» — консервирование элемента; без key — пересоздание/ошибки.
  • «Virtual DOM vs реальный DOM?» — сравнение лёгких деревьев, минимальные изменения в DOM.
  • «useEffect vs useLayoutEffect?» — useEffect после отрисовки (async), useLayoutEffect — до отрисовки (sync, замеры).
  • «Что вернёт render(), если вернуть null?» — ничего не рендерится, но компонент жив.
  • «Можно ли вызвать хук в условном операторе?» — нет, нарушение порядка вызова.
  • «Как передать данные из ребенка в родителя?» — колбэк в props, событие вверх.
  • «Что такое React.memo и когда использовать?» — пропуск ререндера при тех же props.
  • «Suspense для чего?» — fallback для отложенного (lazy/данные) в RSC-мире.
  • «Отличия компонента от элемента?» — элемент = дескриптор { type, props }, компонент = функция/класс.
  • «Как дебажить бесконечный ререндер?» — состояние меняется на каждом рендере (setState в эффекте/теле), чини причину.
Лучшая стратегия: отвечай коротко и по сути, затем пример. «Я бы сделал так...» — уверенность важна.

30 Советы и план подготовки

Советы: делай мини-проекты, читай код чужих компонентов, разберись в хуках глубже поверхностного, решай задачи на собесы вслух.

  • Выучи термины, а не «заученные ответы»: объясняй своими словами («декларативность», «VDOM», «композиция»).
  • Напиши мини-проект сам: список задач (CRUD), фильтр, форма, модалка, роуты — закрывает 80% вопросов.
  • Разбери жизненный цикл: mount → update → unmount в хуках и классах.
  • Потренируй «что выведет код»: порядок эффектов, батчинг, замыкания в обработчиках.
  • Темы для «продвинутого»: React Compiler, RSC, оптимизация, типизация, тесты, perf-профилирование.
  • Читай официальную документацию react.dev (актуально) и русскоязычные материалы — но проверяй версии.
  • Следи за версиями: React 19.2 (2026), React Compiler 1.0 — «новое в React 19» — стабильный вопрос собеса.
  • Покажи проекты: портфолио/код — весомее слов; ссылки на GitHub — приветствуются.
  • Не говори «не знаю» сразу: рассуждай вслух («насколько я помню...», «здесь можно так...»).
Готовность — это не «выучить 30 тем», а «смогу объяснить устройство своего кода». Успехов на собесе! 💪
